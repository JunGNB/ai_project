# v2.1 修复与复标定（M1 / 8 核 GPU / 16 GB）

> 状态：**record**（历史记录，不随代码更新）。
> 时间：2026-11-20 17:04　机器：Macmini9,1 / Apple M1 / 8 核 GPU / 16 GB / macOS 27.0.1 (26A434)
> 环境：AC 供电、热状态 nominal、低电量模式未暴露（`unknown`）、`load_avg_1m = 2.26`、无并发进程
> 工具：macgpu 2.1.0，schema `macgpu/v2`，`--repeat 3`，每指标 9 次采样

## 1. 这一版改了什么

v2.0 的内核和防优化机制是可靠的，问题集中在**统计口径、跨设备映射、错误处理**。v2.1 修了：

| 类别 | 改动 |
|---|---|
| 正确性 | 带宽 `gbps == gbps_max` 是按定义的冗余（不是 bug），补了 `gbps_median` 并在契约里写清 |
| 正确性 | 规格表从子串匹配改为**最长前缀匹配**（M1 Pro 不再被当成 M1） |
| 正确性 | 命令缓冲必须 `status == .completed` 且 `error == nil`；耗时 < 1 µs 直接报错；算力/带宽加物理上界 |
| 正确性 | MCP 摘要改用 `(dtype, path)` 组合键，`fma` 不再覆盖 `mma` |
| 可复现 | 每指标保留 9 个原始样本 + 中位数 + 峰值；结果记录 OS build、热状态、电源、低电量、git sha |
| 可复现 | 带宽线程 65,536 → 262,144；`run` 内嵌自检，失败退出码 2；`run` 加 pid 锁，禁止并发 |
| 自检 | 累加器显式清零；fp16 迭代 96 → 16；GEMM 自检输入改为非二进制精确数（否则误差恒为 0） |
| 文档 | report 第 5 节给 0.8（MLX/MPS）与 0.4（手写）两列；环境告警独立成节；`--eff` 默认 0.8 |
| 通用性 | 无参数 `./macgpu` 即全套；带宽线程自动调优（2× 复测，未饱和自动切换）；部分测试不再覆盖 `latest` |

| GEMM fp32 / fp16 | 0.798 / 1.242 TFLOPS | 0.802 / 1.246 | 0.38% / 0.40% |

自检 12/12：int8/int4 GEMM 误差 0；fp32/fp16 GEMM 6.7e-8 / 9.6e-5；
峰值内核 fp32 4.5e-7、fp16 5.6e-3（阈值 2e-2，余量 3.6 倍）。

> 同一天更早的一次快照（负载 2.0，但另一个 benchmark 并发在跑）只测到 2.06 TFLOPS / 54 GB/s。
> 并发测量会把读数拉低 10~15%，这正是 v2.1 加 pid 锁的原因；引用读数前先确认没有第二个实例。

线程饱和检查（`bandwidth_saturation`）：用 524,288 线程复测 262,144 线程的读数，
读 −0.1% / 写 −0.0% / 拷贝 −1.0%，判定**已饱和**——M1 8 核上默认线程数足够；
大核数 GPU 若出现 ≥3% 的正增益，`notes` 会提示提高 `--bw-threads` 后重测。

## 3. 与 v2.0 基线（records/50）如何对齐

**不要拿 v2.0 的 `value` 直接比 v2.1 的 `value_median`。** v2.0 的 `value` 是 9 次最快，
v2.1 的 `value` 语义没变（仍是最快），`value_median` 才是中位数。

| 项目 | v2.0 记录（22 次，负载 1.37~3.53） | v2.1 本次 |
|---|---|---|
| FP16 矩阵指令 | 2.196 ~ 2.383（峰值） | 2.355（峰值）/ 2.322（中位数） |
| FP16 GEMM | 1.104 ~ 1.250 | 1.246 / 1.242 |
| GPU 读 | 50.1 ~ 60.3 | 58.9 / 58.8 |

带宽中位数与峰值只差 0.2%，说明这次机器很安静；262,144 线程相比 65,536 在空闲时约 +8%
（v2.0 的 65,536 线程普遍落在 54~56 GB/s）。

## 4. 已知限制（本次仍未解决）

- **decode 公式只对 MHA + 小 batch 成立**：GQA 模型 batch 增大后会转为算力受限，
  单看读带宽会低估。
- **热降频未覆盖**：`--repeat 3` 只有十几秒，不足以触发持续满载降频。
- **并发**：同时跑两个 `run` 会互相污染（本次调试中实际观测到带宽从 55 掉到 29 GB/s）。
  v2.1 已加 pid 锁，第二个实例会直接失败。
